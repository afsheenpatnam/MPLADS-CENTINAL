# Deployment Guide

The app deploys as **one service**: in production, the Express server also serves the built
React app (see the `env.nodeEnv === "production"` block in `server/src/app.ts`), so there's no
separate frontend host, no CORS setup, and no cross-origin WebSocket handshake to worry about —
everything is same-origin. A two-service split (API + separately-hosted static frontend) is still
possible and documented at the bottom, but the single-service path is what `render.yaml` and the
steps below use.

## 0. Deploy to Render via GitHub (recommended path)

1. Push this repo to GitHub (already done if you're reading this from the repo).
2. In the Render dashboard: **New +** → **Blueprint** → connect this GitHub repo. Render reads
   `render.yaml` at the repo root and proposes one web service (`mplad-sentinel`).
3. Before the first deploy, fill in the env vars `render.yaml` marks `sync: false`:
   - `MONGODB_URI` — your Atlas connection string (**must include the database name in the path**,
     e.g. `.../mplad_sentinel?appName=...` — not after the `?`, which silently uses the wrong
     database; see `docs/SETUP.md` if you've hit this before).
   - `ASTRA_API_KEY`, `ASTRA_API_URL`, `ASTRA_MODEL` — optional; leave blank and AI summaries show
     "temporarily unavailable" while everything else still works.
   - `CLIENT_URL` — after the first deploy, copy this service's own `https://<name>.onrender.com`
     URL back into this var (only matters as a CORS fallback in a same-origin deploy, but set it).
   - `JWT_SECRET` is auto-generated by the blueprint (`generateValue: true`) — no action needed.
4. Deploy. Render runs `npm install && npm run build` (builds both `server/dist` and
   `client/dist`), then `npm run start --workspace=server`, which serves the API, Socket.IO, and
   the built SPA from one process on Render's assigned `PORT`.
5. Once it's live, seed it or import your CSVs the same way as local dev — `npm run
   seed --workspace=server` needs to be run against the deployed `MONGODB_URI` from your own
   machine (Render's free tier has no shell access), or just use the CSV import flow from the
   live site itself.
6. **Free-tier note**: Render's free web services spin down after inactivity and cold-start on
   the next request (can take 30-60s) — expected, not a bug, if a demo's first load is slow.

If you'd rather set the service up by hand instead of via the blueprint: Build Command
`npm install && npm run build`, Start Command `npm run start --workspace=server`, Health Check
Path `/api/health`, and the same env vars as above.

## 1. Database — MongoDB Atlas

Local `mongod` is fine for development; for anything shared, point `MONGODB_URI` at an Atlas
connection string (`mongodb+srv://...`). No schema migration step is needed — Mongoose creates
collections/indexes on first use. Recommended for production:

- A dedicated database user with read/write scoped to just this database.
- IP allowlisting (or Atlas's "allow from anywhere" only for quick demos, never long-term).
- Enable Atlas backups if the data matters beyond a hackathon demo.

## 2. Backend — Express + Socket.IO

Build with `npm run build --workspace=server` (emits `server/dist`), then run
`node server/dist/server.js`. Requirements for the host:

- **A single long-lived process**, not a serverless/edge function — Socket.IO needs a persistent
  connection, and the ML engine's Isolation Forest is trained once per process (`ensureModel()`
  in `mlEngine.ts` memoizes it) rather than per-request.
- **WebSocket support** on the platform/proxy in front of it (Render, Railway, Fly.io, a plain
  VM, or any host that isn't strictly HTTP-request/response-only). If you must sit behind a proxy
  that only speaks HTTP, Socket.IO falls back to long-polling automatically, but a proxy that
  actively drops `Upgrade` headers will break real-time updates entirely.
- Environment variables from `.env.example` — see the root `README.md`.

## 3. Frontend — served by the same service (default), or split out separately

**Default (what `render.yaml` does)**: `npm run build` builds `client/dist`, and
`server/src/app.ts` serves it directly (static files + an SPA catch-all for client-side routes)
whenever `NODE_ENV=production`. Nothing else to configure.

**If you'd rather host the frontend separately** (Vercel, Netlify, S3+CloudFront) instead of
letting the backend serve it, two things need to change from the default same-origin setup:

- `vite.config.ts`'s dev-only proxy does **not** apply in production — you'd need to point
  `client/src/api/client.ts`'s `baseURL` and `useSocket.tsx`'s `io("/")` call at the backend's
  real deployed origin (e.g. via a build-time `VITE_API_URL` env var) instead of a relative path.
- CORS: `server/src/app.ts` and `socketServer.ts` both restrict `origin` to `env.clientUrl` — set
  `CLIENT_URL` to the separately-hosted frontend's real origin so the browser's CORS and Socket.IO
  handshake checks pass.

## 4. File storage — evidence & documents

**Current state**: `server/src/middleware/upload.ts` writes uploaded evidence/documents to a
local `uploads/` directory, served back via `express.static`. This is fine for development and
for this hackathon prototype, but **local disk storage does not survive a redeploy or scale past
one instance** on most PaaS hosts (ephemeral filesystems).

**For a real deployment**, replace the disk storage with an object-storage-backed multer engine:

- `multer-s3` (or any S3-compatible bucket — AWS S3, Cloudflare R2, MinIO), or
- `multer-storage-cloudinary` for Cloudinary.

The integration point is exactly one file: swap the `multer.diskStorage(...)` in
`server/src/middleware/upload.ts` for the chosen engine's storage adapter, and change
`evidenceController.ts`/`documentController.ts` to store the returned URL instead of a local
filename (`Evidence.filePath` / `ProjectDocument.filePath` currently store a bare filename served
from `/uploads/<name>` — store a full URL instead when using cloud storage, and update
`client/src/api/client.ts`'s `fileUrl()` helper accordingly). This was intentionally left as
local-disk-only in this codebase rather than wiring in an untested cloud integration with no
real credentials to verify against — swapping it in is a contained, well-scoped change.

## 5. Secrets

Never commit `.env`. `.gitignore` already excludes `.env`, `.env.*` (with `.env.example` allowed
back in), `node_modules`, `uploads`, `dist`, `build`, `coverage`. Rotate `JWT_SECRET` and
`ASTRA_API_KEY` if either is ever accidentally exposed.

## 6. CI

`.github/workflows/ci.yml` runs `npm install`, `lint`, `typecheck`, `test`, and `build` on every
push/PR — treat a red CI run as a merge blocker (see `CONTRIBUTING.md`).
